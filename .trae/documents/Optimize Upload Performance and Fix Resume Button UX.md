我将实施以下计划，解决浏览器卡顿问题并修复续传按钮无法点击的 bug。

### 1. 解决浏览器卡顿与掉帧 (GC & Memory Leak)

* **问题分析**：

  * 目前代码在上传分片时，`uploadLogs` 数组会不断累积日志。虽然有 `MAX_LOG_LINES` (2000) 限制，但在高频更新（每个分片上传前后都写日志）时，Vue 的响应式系统 (`ref`) 处理大量字符串数组的更新开销较大。

  * 更严重的问题可能在于 `localStorage.setItem` 的频繁调用。每次分片上传成功或进度更新，都会调用 `snapshotSession`，进而触发 `JSON.stringify` 并写入 `localStorage`。对于大文件，这可能触发成百上千次同步的 I/O 操作，阻塞主线程，导致 UI 卡顿和掉帧。

* **解决方案**：

  * **减少日志量**：降低日志详细程度，或仅在错误/关键节点记录日志，不再每个分片都记录详细信息。

  * **节流存储 (Throttle)**：对 `snapshotSession` 或 `writeUploadSession` 进行节流 (Throttle)，例如每 5 秒或每上传 10 个分片才写入一次 `localStorage`，而不是实时写入。这是解决卡顿的关键。

  * **内存优化**：确保 `chunk` 变量在循环结束后能被及时垃圾回收 (GC)。目前的 `for` 循环结构通常没问题，但如果 `log` 函数持有了大量长字符串引用，也会增加 GC 压力。

### 2. 修复“继续上传”按钮无法点击

* **问题分析**：

  * 按钮的 `disabled` 属性绑定了 `!file`。

  * 当页面刷新或重新进入时，浏览器出于安全原因，**不会**保留 `<input type="file">` 中的文件对象。因此 `file` 变量为 `null`。

  * 用户看到“检测到未完成的上传”提示，但因为 `file` 是空的，按钮一直灰显。用户必须先在下方的 "ND2 File" 输入框中**重新选择同一个文件**，`file` 变量有了值，按钮才会变亮。

  * **UX 缺陷**：用户不知道需要重新选择文件，或者选择了文件后逻辑没有自动关联。

* **解决方案**：

  * **提示优化**：在 Alert 区域明确提示用户“请重新选择文件以继续上传”。

  * **逻辑优化**：

    * 当检测到恢复会话 (`hasRestoredSession`) 时，允许文件选择框处于可用状态（目前 `disabled="uploading"` 是对的，但如果 `hasRestoredSession` 为 true 时不应禁用选择框，代码中 `disabled` 逻辑看似没问题）。

    * 关键是：用户重新选择文件后，`handleFileSelect` 会更新 `file` 变量。此时 `canResumeMultipart` (检查 session) 和 `file` (检查当前选择) 都满足，按钮应自动变亮。

    * **改进**：添加一个显式的状态提示，或者如果用户选择了文件且匹配 Session，自动激活 Resume 流程（可选，但手动点击更安全）。

    * **Bug 修复**：目前的 `handleFileSelect` 逻辑可能没有处理“恢复模式”下的校验。我们需要确保用户选择文件后，如果处于恢复模式，进行文件名和大小的比对，匹配则允许 Resume，不匹配则报错。

### 3. 具体修改步骤

1. **修改** **`TaskCreate.vue`**:

   * **节流存储**：引入 `lodash/throttle` 或手动实现节流，限制 `writeUploadSession` 的频率。

   * **优化日志**：减少 `log()` 调用，避免在进度更新中频繁记录。

   * **UI 改进**：在“未完成上传”的 Alert 中添加文字提示：“请在下方重新选择文件 **{fileName}** 以激活继续按钮”。

   * **逻辑修正**：确保文件选择后，Resume 按钮状态能正确更新。

### 4. 验证方案

* 上传一个大文件，中途刷新页面。

* 观察“继续上传”按钮状态（应为禁用）。

* 根据提示重新选择同一文件。

* 观察按钮是否变亮（可用）。

* 点击继续，观察上传过程是否流畅，不再出现严重的浏览器卡顿。
